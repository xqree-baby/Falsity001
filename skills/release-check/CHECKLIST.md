# 发布前检查项清单（release-check）

> 本文件是 `SKILL.md` 的**设计依据**，说明每一项「为什么存在」「怎么判过」「怎么判不过」。
> Day 25 建立，之后每次发布前跑一遍。

## 一、为什么要做这个

一个检查工具最大的风险不是**漏报**，而是**虚报通过**——查不出问题却报告「全部通过」。
漏报你会怀疑，虚报你会直接信，代价更大。

因此本 Skill 有一条铁律，写在 SKILL.md 最前面：

> **没跑过「故意弄坏」验证的 Skill，不许被当作「通过」的证据。**

配套的验证方法（Day 25 板块③ 实跑）：故意注入一个已知问题 → 跑 Skill → 它必须报警 → 修掉 → 再跑 → 必须干净。
**只有「坏的时候报警、好的时候安静」两头都成立，才算这个 Skill 可信。**

## 三、逐项设计

### C1 密钥泄漏 ✅ 本次实现

**为什么**：Day 23 排过一次，结论是 0 条。但「上一次排过」不等于「现在还干净」——这中间改过代码（Day 24 改过 `functions/api/index.js`）。密钥一旦进库，git 历史里删掉也算泄漏，必须发布前重扫。

**怎么判过（全部满足）**：
1. 没有任何 `.env` / `.env.*` 文件被 git **跟踪**（`git ls-files` 查得到就是泄漏）
2. 全仓库扫描「密钥变量名 + 字面量」的组合，命中 **0 条**
3. 唯一存在的 `.env` 文件处于被忽略状态

**明确不算泄漏的写法**（Day 23 已经踩过这个坑，不能再误报）：
- `process.env.CLOUDBASE_API_KEY` —— 取变量名，不是值
- `Bearer ${API_KEY}` —— 模板字符串，运行时才填值
- `'CLOUDBASE_API_KEY 未配置'` —— 中文错误提示里的变量名
- `"local-test-not-a-real-key"` —— 明显标注为假值的测试桩

**关键点：判定条件是「变量名附近有没有一个像密钥的**字面量**」，不是「有没有出现变量名」。**
只看关键词必然误报一堆——`functions/api/db.js` 里有 6 处 `Bearer ${API_KEY}`，全是干净的。

**怎么判不过**：出现 `xxx_KEY = "一段像密钥的字符"` 或 `.env` 被 `git add` 过 → 报警。

### C2 公网可达性 ✅ 本次实现

**为什么**：这个项目最阴的坑是**「后端活着但前端拿不到」**。Day 20 跨域头配了两遍，浏览器网络层直接把响应掐掉，前端只拿到 `Failed to fetch`，连状态码都读不到——看起来像后端挂了，实际后端好好的。

**怎么判过（全部满足）**：
1. 接口域名可达：请求 `/api/posts`，拿到 HTTP 200 且返回体是合法 JSON
2. **响应头只有一个** `access-control-allow-origin`（逗号拼接成两个值 = 配重了 = 浏览器会掐）
3. 静态托管域名可达：首页返回 200

**怎么判不过**：
- 连不上 / 超时 / 非 JSON → 报警
- ⚠️ **`{"code":"INVALID_PATH","requestId":...}`** = 网关路由没绑（Day 22 实测）
- ⚠️ **`{"ok":false,"error":"not found","receivedPath":"/api/posts"}`** = 函数里少注册分支（Day 24 的病根）

这两种 404 长得像但根因完全不同、**修的位置完全不同**（一个改网关配置，一个改代码）。检查项必须能区分开，否则报了也等于没报。

**判据边界（必须写进 SKILL.md，否则会误判）**：
- 只探活**线上**，不去改任何线上数据
- 探活只发 **GET**，不发 POST/PATCH/DELETE——避免污染数据库、避免撞唯一索引（Day 23 已知 7 篇帖全被收藏过，再 POST 会 409）
- 静态托管 URL **每次重部署都会变**，检查前必须先确认当前 URL，读代码里写死的那份
